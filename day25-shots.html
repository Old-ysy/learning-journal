$ bash preflight-check.sh
① 密钥 · 工作区扫描
[PASS] 工作区没有疑似密钥（脱敏文本不算命中）
⑥ 线上代码是最新（本地改动已经部署上去）
[FAIL] 线上跑的不是本地这份代码
本地 md5 af44e6973304… / 线上 md5 4ea30ae218ea…
→ 改完代码别忘了重新部署，页面能开 ≠ 代码是最新的
结果：6 通过 / 1 失败
第 ⑥ 项这条是真问题，不是我故意的 —— Day 24 改的 app.js 一直没重新部署， 而页面照常能打开，肉眼根本看不出来。这正说明需要这个 Skill。

② 故意弄坏一项：往工作区塞一个假密钥

# .workbuddy/tmp/sabotage-fake-key.txt（假串，EXAMPLEFAKE，不是真凭证）
const TOKEN = 'ghp_EXAMPLEFAKE0123456789abcdefghijkl';

③ 再跑一遍 —— 它被查出来了

$ bash preflight-check.sh
① 密钥 · 工作区扫描
[FAIL] 工作区发现疑似密钥，1 处：
./.workbuddy/tmp/sabotage-fake-key.txt:3:const TOKEN = 'ghp_EXAMPLEFAKE…';
② 密钥 · git 历史扫描
[PASS] 全部历史分支里没有「真密钥形态」的串
③④⑤⑦ …
[PASS] 首页 200 · 接口 ok:true · 资源无 404
结果：6 通过 / 2 失败
精确到文件名 + 行号 + 内容 —— 不是笼统报「有风险」，是能直接照着去改。
而且它没有被我那句「这是测试夹具」的注释骗过去。

④ 把假密钥删掉，再跑一次

$ rm .workbuddy/tmp/sabotage-fake-key.txt && bash preflight-check.sh
[PASS] 工作区没有疑似密钥（脱敏文本不算命中）
结果：6 通过 / 1 失败　← 只剩第 ⑥ 项那条真问题
这一趟最关键：它能变回 PASS。只会永远报红的检查等于没有检查 —— 能报红、也能转绿，才说明它看的是真实状态，不是写死的结论。

检查项怎么定的 · 以及修掉的一个误报

Day 25 · 板块①规划 / 板块②制作

七项检查，分三组

组检查项为什么它必须进发布前检查
安全① 密钥 · 工作区扫描漏一次就是公开仓库裸奔，且撤销成本极高
② 密钥 · git 历史扫描删文件没用，历史里还在 —— 很多人只查当前文件
③ .env 未入库且被忽略查的是「gitignore 有没有真的挡住」，不是「文件在不在」
公网④ 首页可达托管没部署 / 域名失效，本地怎么试都发现不了
⑤ 接口健康（ok:true）首页 200 但接口挂了，页面看起来只是「没数据」
⑥ 线上代码是最新比 md5，不看文件大小：页面能开 ≠ 代码是最新的
资源⑦ 线上引用无 404css/js 404 只是变丑、不报错，最容易蒙混过关

今天修掉的一个误报（Skill 自己也需要被验证）

第一次实跑时 ② 项报 FAIL，指着 Day 23 和 Day 6 两个提交。查下去发现命中的是 grep ghp_ .git/config 这条规则文本本身和截图页里的 ghp_××××… 脱敏展示 —— 真密钥一条没有，远端是干净的。
于是把判定收紧成两段：先用 git log -S 粗筛候选提交， 再对每个提交做「真密钥形态」精筛（前缀 + 20 位以上连续字符）。 规则文本和脱敏串都不再命中，真密钥照样跑不掉。

今日一问：你故意弄坏哪一项来验证 Skill 不会虚报通过？

弄坏的是「密钥 · 工作区扫描」。
选它的理由：这是漏报代价最大的一项 —— 别的项漏了顶多是线上难看， 这项漏了是凭证进公开仓库，且撤销成本极高。所以必须拿最难糊弄的一关来验证。

做法：往工作区塞一个形态逼真的假密钥（ghp_ + 26 位字符）， 看它能不能从几千个文件里揪出来。它揪出来了，还给到了行号。

而且只验证「能报红」不够 —— 又删掉重跑了一次，确认它能转绿。 不会转绿的检查，跟永远绿着一样不可信。
